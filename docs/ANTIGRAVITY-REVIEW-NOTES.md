## Corrections required in the next batch

**Blocking review of the in-progress auth edit:** `finalPasswordHash = newPasswordHash ?? user.passwordHash` reintroduces QA004 for legacy/API signups: a verification POST with email/token but no fresh password promotes the original attacker-chosen hash. Never fall back to an unverified stored hash. Require a freshly supplied owner password for unverified activation even when a stored hash exists. Invalid/missing password attempts must not consume the owner's single-use verification link; the current return-false result after `consumeToken` commits its deletion. Add a regression for attacker signup -> no-password confirmation rejected -> same token plus owner password succeeds -> original password fails. Preserve established accounts under concurrent operations as requested below.

The subsequent catch-all `catch (err) { return { error: err.message } }` must not serialize unexpected database/session errors to the client. Drizzle errors can contain SQL and bound values. Distinguish expected activation validation errors from unexpected failures; return safe user-facing messages and preserve the correct retry/server-error behavior. Test that an unexpected failure cannot expose query details or credential hashes.

1. **Auth ownership race:** `confirmEmailVerification` reads account verification and OAuth linkage outside its transaction, hashes asynchronously, then performs an unconditional update by email inside the transaction. Another verification token, password reset or Google linkage can change the account between those steps. Move the authoritative ownership/state decision into a transaction with appropriate row locking or conditional updates; preserve already established credentials. Test two distinct valid verification tokens and activation versus reset/linkage, not only replay of an already consumed token. Ensure inactive/missing accounts cannot obtain a session through the changed paths.
2. **Signup product flow:** the initial signup still asks for a password, and verification asks for a fresh one again. Make the owner activation step understandable and avoid an unexplained discarded password. Prefer one clearly explained point where the mailbox owner establishes the final password; align server schema, UI, email copy, recovery and return URLs. Do not weaken ownership safety or optional Google sign-in.
3. **Evidence accuracy:** `REMEDIATION_LOG.md` has VERIFIED entries without per-entry commands, execution times or evidence links. Distinguish implemented, source-reviewed, regression-tested and browser-tested. Preserve the original audit baseline; do not rewrite its findings as if they never existed.
4. **Regression harness:** `tests/integration/qa004-ownership-regression.mjs` is not discovered by the current Vitest integration include (`**/*.test.ts`). Add meaningful automated regression coverage to the normal disposable test harness rather than relying exclusively on an ad hoc script that mutates the preserved audit database. Never print credential-bearing database URLs even in a safety-check failure. Synthetic test constants in test source are fine; raw identities, sessions, mail and database contents belong only in ignored evidence. Assert the pre-verification session really existed before testing revocation. A consumed-token replay alone does not test a different still-valid token after another ownership action.
5. **Field error mapping:** onboarding currently identifies URL/name fields by searching human error strings and stores a name error without visibly wiring that state to an input. Application form assigns every form/server/network error to the current text input. Use meaningful field validation versus form/network errors, preserve alerts and retries, and focus the actual invalid control or summary. Test name errors, offline/retry, and non-text question types as well as the original URL case.
